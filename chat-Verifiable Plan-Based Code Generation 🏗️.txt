The previous discussion critiqued the naive chain of disconnected review gates and proposed a state-machine model where the plan is a versioned, structured artifact. Here is the detailed breakdown of that approach so you can begin implementation:

### 1. The Core Schema: `Plan` and `SystemState`
Instead of passing a blob through reviewers, the planner emits a typed `Plan` struct. The `SystemState` tracks which stage of the graph the implementation is currently at.

```typescript
type TaskNode = {
  id: string;
  description: string;
  dependencies: string[];
  expected_output_type: string; // Used by the reviewer as the "contract"
};

type Plan = {
  id: string;
  version: number;
  graph: TaskNode[];
  metadata: Record<string, any>;
};
```

### 2. The Planner and the Reviewer
The **Planner** (smart model) does not write code. Its only output is the `Plan`. The **Reviewer** then walks that graph and confirms each node matches the intended behavior rather than giving a pass on the whole blob. Once locked, the plan becomes a verifiable contract for the coder.

### 3. The Coder
With a locked `Plan`, the coder model generates implementation only for the nodes the system is currently executing. The coder never sees a "mutable" plan; it works from a validated contract, which drastically reduces hallucinated drift during generation.

### 4. The Verifiable Loop
The "QA" gate is replaced by a dedicated test runner. After the coder finishes a node, the system runs it against a pre-defined test suite. The final review then verifies that the test results match the expected outcomes, replacing subjective review with a verifiable loop.

### Implementation Walkthrough
1.  **Emit the Plan:** The planner produces the `Plan` JSON.
2.  **Lock the Plan:** The reviewer validates the graph structure and `expected_output_type` for every node.
3.  **Locked Implementation:** The coder executes against the `Plan` graph.
4.  **Test Run:** A test runner executes the generated code.
5.  **Final Verification:** The final smart model review verifies test pass/fail against the contract.

To build out from the high-level architecture, we need to materialize the "locked plan" and the state machine. The core idea is to treat the `Plan` as a versioned artifact: the planner emits the graph, the reviewer locks it (rejecting the whole plan on failure), and then the coder can execute it node by node without the plan drifting under its feet.

### 1. The Schema

```typescript
type TaskNode = {
  id: string;
  description: string;
  expected_output: string; // The contract for the coder
  test_case: string;       // The contract for the QA runner
};

type Plan = {
  id: string;
  version: number;
  nodes: TaskNode[];
};

enum ExecutionStatus {
  PLANNING = 'planning',
  REVIEWING = 'reviewing',
  CODING = 'coding',
  VERIFYING = 'verifying',
};

interface GraphState {
  plan: Plan | null;
  status: ExecutionStatus;
  current_node_idx: number;
  errors: string[];
}
```

### 2. The LangGraph Walkthrough

The graph walks the plan after the reviewer gate:

- **`planner`**: Converts the raw context into the `Plan` object.
- **`reviewer`**: Iterates `plan.nodes` and compares each `TaskNode` against the required spec. If any node fails validation, the cycle is broken.
- **`coder`**: Only sees the `nodes[current_node_idx]` and the `expected_output`, removing the possibility of the coder hallucinating side effects in the rest of the system.
- **`qa`**: A non-llm runner that imports the generated code and executes it against `test_case`.
- **`final_reviewer`**: Verifies that the test runner's stderr/stdout matches the expected test results.

### 3. Concrete Example: `add_user_to_db`

Let's walk through how this looks for a simple database write task:

**1. The Planner's Output (the locked contract):**
```json
{
  "plan": {
    "id": "user-add",
    "version": 1,
    "nodes": [
      {
        "id": "parse_request",
        "description": "Parse the JSON request body",
        "expected_output": "valid_request_params",
        "test_case": "input={'id':1, 'username':'jdoe'} -> expected: {'parsed':true}"
      },
      {
        "id": "validate_user",
        "description": "Check if user exists or has valid credentials",
        "expected_output": "user_validated",
        "test_case": "input={'username':'jdoe'} -> expected: 'valid'"
      },
      {
        "id": "execute_insert",
        "description": "Insert into database",
        "expected_output": "db_success",
        "test_case": "mock_db_insert -> expected: 201"
      }
    ]
  }
}
```

**2. The Coder's Execution:**
Instead of trying to generate the entire 3-node workflow in one pass, the coder is called once per node. For node `parse_request`, it gets the `expected_output` contract and a sample input; it produces only the parsing logic. Once that passes `qa`, the state increments `current_node_idx`, and the coder starts on `validate_user`.

**3. The Verifiable Loop:**
The final gate replaces the subjective "looks good" check from the old flow. Each node's `test_case` is a deterministic script; the `final_reviewer` only marks the node as "done" when the runner returns success. If `qa` fails, the `errors` list is appended and the system halts—no hallucinations allowed past the verification gate.

The system treats dependencies as a directed acyclic graph (DAG) at plan-lock, which the state machine then linearizes into a deterministic execution order. Instead of a single monolithic generation pass, the `coder` and `qa` layers walk that sorted list, with each stage operating only on the current node's subtree of the locked `Plan` artifact.

### Schema and Structure

The `Plan` holds the full directed graph, while `SystemState` tracks the linear progress through it:

```typescript
type TaskNode = {
  id: string;
  description: string;
  dependencies: string[]; // Adjacency list for the DAG
  expected_output_type: string;
  test_case: string;
};

type Plan = {
  id: string;
  version: number;
  graph: TaskNode[];
};

enum ExecutionStage {
  PLANNING,
  REVIEWING,
  CODING,
  VERIFYING,
};

interface SystemState {
  plan_id: string;
  current_node: string;
  stage: ExecutionStage;
  history: Array<{ node_id: string; status: 'success' | 'failure' }>;
};
```

### Execution Walkthrough

1. **Plan Generation and Locking**: The planner emits the full `Plan`. A topological sort is calculated during the `REVIEWING` stage; the reviewer validates the graph's acyclicity and that every `dependency` id exists within the `graph`. Once passed, the plan is locked and the `plan_version` is promoted.

2. **Directed Coder Pass**: The `coder` model is invoked for one `TaskNode` at a time. It is given only the current node and a distilled "contract" from the preceding nodes in the dependency chain, which prevents it from hallucinating side effects in the rest of the graph.

3. **Deterministic QA**: After a node's implementation is generated, the system executes the `test_case` for that node in isolation. A pass here is the signal to advance to the next node in the sorted sequence; a failure breaks the chain immediately and records the error in `SystemState`.

4. **Verifiable Completion**: The final `VERIFYING` stage does not re-review the code; it verifies the `history` of the execution against the expected outcomes of the `Plan` graph. A passing execution trace is the final gate for acceptance.
